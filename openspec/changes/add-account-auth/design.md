## Context

Gateway currently creates an in-memory `player_id` as soon as the ctrl TCP connection is accepted, sends `SessionWelcome`, and publishes `player.joined`. `SessionRegistry` assigns IDs from a process-local counter. MetaDB stores numeric IDs in `players` and keys inventory, quests, rewards, cooldowns, and position by those IDs, so an ID reused after reconnect/restart can refer to the wrong or empty profile. There is no current account authentication source. The current `add-multiplayer-foundation` proposal explicitly excluded accounts/tokens.

The user selected a simple self-written registration/login system, stable identity across reconnect/restart, no automatic migration of old numeric profiles, and explicitly accepted plaintext transport for their private deployment.

## Goals / Non-Goals

- Goals: registration/login, durable account subject, stable mapping to existing numeric gameplay `player_id`, auth-before-session activation, and isolation between credentials/account policy and game handlers.
- Non-Goals: public/hostile-network security, automatic legacy profile migration, third-party identity providers, account recovery/MFA, multi-device account management, or a broad auth platform.

## Decisions

- **Library boundary:** create a reusable Go auth package for username policy, password hash/verify, and typed auth outcomes. MetaDB remains the persistence owner and injects an account repository into that package. Gateway uses a narrow MetaDB auth RPC adapter; do not put passwords/tokens on MessageRouter or mix password policy into C++ gameplay handlers. Avoid CGO or duplicated crypto logic.
- **Identity model:** create an immutable account UUID subject, normalized unique username, password hash, and a unique account→numeric `player_id` mapping. Continue using numeric `player_id` throughout current gameplay/protocol/database tables.
- **Username canonicalization:** reject invalid UTF-8; trim only leading/trailing ASCII space and horizontal tab (`0x20`, `0x09`); convert ASCII `A`–`Z` to lowercase; then require 3–32 bytes matching `[a-z0-9_]+`. Apply exactly this function before registration uniqueness checks and before login lookup; persist only the canonical username.
- **Password and KDF parameters:** password SHALL be valid UTF-8 of 8–128 bytes inclusive for both registration and login. Hash using Argon2id v1.3 with `t=3`, `m=65536 KiB`, `p=1`, 16 random salt bytes, 32 output bytes. Store an explicit versioned encoding containing algorithm and parameters. During verification, reject stored encodings outside configured safety bounds (`t<=6`, `m<=262144 KiB`, `p<=4`, salt 16–64 bytes, output 32–64 bytes) before allocating KDF memory. At most 2 Argon2id operations may run concurrently per MetaDB process; excess work waits only until the auth RPC deadline, then fails generically.
- **Fresh player-ID allocation:** within the account-registration transaction, allocate the next numeric player ID above the persisted high-water mark and above all existing `players.id` rows, including legacy rows. Persist the allocator state transactionally so IDs are never reused after deleting a profile or restarting MetaDB. Fail closed at signed 64-bit integer exhaustion.
- **Legacy rows:** registration creates a new player row and mapping transactionally. Existing numeric player rows remain unmapped and are not claimed by username, nickname, or a client-chosen ID.
- **Gateway lifecycle:** accepted ctrl sockets begin unauthenticated. No player ID welcome, `player.joined`, profile restore, bulk pairing, or gameplay action admission before valid auth. A 15-second deadline starts at ctrl accept and covers frame reception, RPC, and password hashing; partial frames or retries do not extend it. Any timeout or malformed/unexpected frame closes the pending connection without player side effects. A bounded failed-authentication `AuthResult` leaves the unauthenticated connection available for another login attempt, but every attempt remains within the original, non-extendable 15-second accept-to-auth deadline; no player side effects occur before success. An authenticated, established session that disconnects and later reconnects with invalid saved credentials SHALL release that transport, clear those in-memory credentials, and return to manual login without automatic retrying the rejected password. After success, bind the persistent numeric player ID and stable account subject to the ephemeral `session_id`; `SessionHello` continues to pair bulk by that transient session ID.
- **Concurrent sessions:** allow one active session per account initially; an atomic Gateway-local account reservation rejects concurrent logins, is released on authenticated-session disconnect and pre-auth timeout, and is cleared when the single Gateway process restarts. This assumes exactly one authoritative Gateway instance; multi-Gateway deployment is out of scope.
- **Credential storage:** use `golang.org/x/crypto/argon2` Argon2id with the exact parameters above and a versioned encoded hash. Bound request/input sizes before hashing; allow at most 5 failed attempts per normalized account name and at most 20 failed attempts per remote IP in any rolling 15-minute window. Return generic login failures and never log plaintext passwords, hashes, or bearer credentials. Adding this maintained dependency is part of this change.
- **Transport scope:** this version is trusted LAN/VPN only and explicitly uses plaintext TCP. Credentials and session data can be sniffed, replayed, or tampered with on an untrusted network. Do not claim public-network security; adding TLS is a required future change before exposing the service beyond trusted networking.
- **Legacy API:** disable every legacy JSON action that reads or mutates player data using a caller-supplied numeric ID (`login`, `logout`, `update_slot`, `delete_slot`, `save_position`). None is retained as a client compatibility or internal bypass path in this change. Keep only non-auth diagnostic JSON actions on the legacy listener; it binds to loopback by default and an explicit private bind is required for remote diagnostics.

## Risks / Trade-offs

- Plaintext registration/login is unsafe on untrusted networks; this is an explicit deployment limitation, not mitigated by hashing passwords at rest.
- Account mapping in MetaDB creates a durable identity boundary. New account IDs must not accidentally attach existing numeric profiles.
- Login-before-join changes the current eager Gateway session path and requires strict ordering so no player state leaks before authentication.
- A private auth RPC must be protected from arbitrary network clients and must have bounded frames/timeouts.
- Use the existing MetaDB direct FlatBuffers RPC framing on a dedicated auth listener bound to `127.0.0.1:5007` by default; allow an explicit private-interface bind for split-host trusted deployments. It is distinct from the general gameplay RPC listener at `127.0.0.1:5006` by default and the legacy JSON API at `127.0.0.1:5005`; the latter two may bind a private interface only by explicit configuration. Auth is not exposed through MessageRouter. Apply a 64 KiB auth request/reply frame limit and a 3-second per-request deadline.
- The legacy JSON listener remains enabled only on loopback by default for non-auth diagnostics; a private-interface bind is explicit configuration. Its caller-supplied numeric-ID `login` action SHALL be disabled and return a generic unsupported/unauthenticated error on all binds.
- Ctrl auth uses the existing control connection: before authentication, the client may send only explicit register/login requests. Gateway returns a distinct generic AuthResult; only success is followed by SessionWelcome. No new client-facing auth port is added. The ctrl transport stays plaintext in this trusted-network-only change. Accepted ctrl sockets have a 15-second pre-auth deadline, accept only bounded auth frames until success, and cannot pair bulk or send gameplay before successful auth.
- The game client uses a pre-game ImGui login/registration screen. Credentials remain in process memory for transport reconnects, and after successful AuthResult the client stores the username/password in a per-user local credential file for later launches. Auto-login still uses the existing login action; a rejected saved password is removed and the manual form remains available with the username prefilled. Explicit disconnect clears in-memory credentials but does not remove the saved file.
- Credential storage is client-side and deliberately plaintext at rest, per user choice. The client uses `$XDG_CONFIG_HOME/gtnh-platform/account-credentials.json` when XDG_CONFIG_HOME is absolute, otherwise `$HOME/.config/gtnh-platform/account-credentials.json`. The directory is mode 0700 and the file mode 0600. Reads reject symlinks, non-regular files, invalid ownership/permissions, malformed JSON, and files larger than 4 KiB. Writes use a unique same-directory temp file, restrictive creation mode, fsync, atomic rename, and directory fsync. Missing/unsafe files disable auto-login without blocking manual login; save failure does not undo successful server authentication. Never log credential contents. The file remains accessible to the same user, root, malware running as that user, and backups.
- Registration policy: username is trimmed only for surrounding ASCII whitespace, normalized to lowercase ASCII `[a-z0-9_]`, length 3–32; passwords are 8–128 UTF-8 bytes. Login uses the same normalized name and returns the same generic invalid-credentials response for unknown users and wrong passwords.

## Migration Plan

No legacy profile migration occurs. New registrations allocate fresh numeric `player_id` values and create account mappings. Existing numeric rows continue to exist but remain inaccessible through account login unless a separate, explicitly approved migration is designed later.
